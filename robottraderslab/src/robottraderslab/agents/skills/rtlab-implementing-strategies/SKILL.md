# Implementing a RobotTradersLab strategy

A strategy is a Python package of its own, beside the project folder.

Start from the moving average crossover template strategy: a profile strategy that trades the crossing of a fast and a slow moving average, its profile carrying the two periods and the sizing, and that backtests and produces trades as written. Step 1 of the Workflow section below writes it into the package.

## Where the facts are

The installed engine is the authority on every signature, argument and configuration key, since it is the version that runs:

```bash
uv run python -m pydoc robottraderslab.strategies.ProfileStrategy
uv run python -m pydoc robottraderslab.strategies.futures.FuturesAccount
```

`robottraderslab.indicators` holds the indicators its `__all__` lists, among them `crossover(series, other)` and `crossunder(series, other)`, True on the candle where one series crosses the other, and `value_periods_ago(series, periods)`, the value a series held `periods` candles earlier, on every candle; any other indicator is computed with numpy in the signals phase.

Three strategies show how the contract below is met beyond the template strategy. Read one only for the case it covers:

- `futures_ma`, the engine's moving-average crossover and the template strategy's fuller version: a whole profile strategy in one file, with its signals, a trend filter, entries and exits, a position tracker and chart lines. Read it when the strategy needs a trend filter, a position tracker or chart lines. It is the module `robottraderslab.ma_strategy.futures_ma_strategy`, installed with the engine, and `uv run python -c "import robottraderslab.ma_strategy.futures_ma_strategy as m; print(m.__file__)"` prints its path.
- Impulse, https://github.com/RobotTraders/RobotTradersLab/tree/main/plugins/robottraderslab-impulse under `src/robottraderslab_impulse/`: several profiles on one symbol, such as one market on several timeframes or parameter sets, whose orders the venue nets into one position, so each profile tracks its own position through tagged orders, and a stop-loss restated on every candle. Read it when profiles share a symbol or when the strategy protects its positions.
- Envelope, https://github.com/RobotTraders/RobotTradersLab/tree/main/plugins/robottraderslab-envelope under `src/robottraderslab_envelope/`: entries on limit or trigger orders at several price levels, resting across candles, and a side kept from entering again after its stop-loss fires, a state rebuilt from the account's fills, and its cancels and new orders booked with `after` (contract rule 6), so each symbol's new orders wait only for that symbol's cancels and a live cycle places the symbols at the same time. Read it when the strategy enters on resting orders, keeps state across cycles or books actions that wait only for some earlier ones.

Read Impulse and Envelope from their folders in the public repository: they may not be installed.

The published documentation pages, each for what it holds:

- Implement a strategy, the code of a strategy section by section, from its requirements, signals and booking to its order kinds, sizing, protections and state, and its registration and configuration: https://robottraders.io/lab/docs/implement-a-strategy.html
- Ship a strategy, the strategy's folder beside the project, its private repository and its install on a VPS: https://robottraders.io/lab/docs/ship-a-strategy.html
- API reference, every public symbol with its arguments: https://robottraders.io/lab/docs/reference.html
- Data sources, the candle sources a bot's configuration file can name: https://robottraders.io/lab/docs/data-sources.html

## Workflow

1. **For a new strategy, ask the user what to name it**, then set up its package with `rtlab new strategy`, the command that writes the template strategy as a package of its own for the user's strategy to replace. Run it from the project folder or any folder inside it, with the package's folder as its argument, a path from the project folder to a folder beside the project, never inside it. `<name>` stands for the user's name for the strategy, in lowercase letters and digits joined by single dashes or underscores, and no Python keyword:
   ```bash
   uv run rtlab new strategy ../<name>
   ```
   The command writes:
   - the package in `../<name>/`: `pyproject.toml`, `.gitignore`, `src/<module>/__init__.py`, `src/<module>/main.py` and `src/<module>/chart_indicators.py`, where `<module>` is `<name>` with its dashes as underscores;
   - in `main.py`, the template strategy's class `<Class>` and its profile class `<Class>Profile`, `<Class>` being the words of `<module>` capitalised and joined, with `Strategy` added unless the capitalised result already ends with `Strategy` (`momentum_ma` gives `MomentumMaStrategy`, `mystrategy` gives `MystrategyStrategy`);
   - in `pyproject.toml`, the distribution name `<name>`, the dependency on the installed engine version and two entry points under the key `<module>`: one registers `<Class>`, the other registers `chart_lines` of `chart_indicators.py`, which draws the fast and the slow average on the chart of the backtest's `report.html`;
   - the bot's configuration file `workspace/<name>/bot.toml`, its `strategy_class` set to `<module>`.

   The command then installs the package in the project, editable, as `uv add --editable` does, so the next run executes the package as it is on disk. None of these names needs an edit by hand: write no entry point, rename no class and run no `uv init`, `uv add` or `uv sync`. It refuses a package folder or a bot folder that exists, a name that cannot be a Python package name, and a name whose class would be `ProfileStrategy`, which the engine's own class holds, and a name that is already an importable module or a registered strategy; ask the user for another name then. If the install fails, the files stay written and the message names the `uv add` line; give that line to the user to run, and run no other install yourself.
2. **Code the strategy and configure its bot.** In `src/<module>/main.py`, change the template strategy's class into the user's strategy, its crossing of two moving averages replaced or built on, and in `src/<module>/chart_indicators.py` the lines of `chart_lines` changed with it, so the report draws what the strategy trades. The bot configuration file, `workspace/<name>/bot.toml`, is a TOML file: plain text of `key = value` settings grouped under `[section]` headings. `rtlab backtest` reads it for a backtest and a live run reads it to trade. Its sections:
   - `[strategy]`: `strategy_class` names the strategy by its entry-point key, and every other key is a setting of the strategy class.
   - `[[strategy.profiles]]`: one profile, a market with its timeframe and parameters; the section repeats once per profile.
   - `[backtest]` and `[backtest.ohlcv_provider]`: the balance, the fees and the dates of a backtest, and the source of its candles.
   - `[live.ohlcv_provider]` and `[live.trading_account]`: the candle source and the account of a live run. The command writes neither; a live run needs both, and Going live, https://robottraders.io/lab/docs/going-live.html#configure-the-bot-for-live-trading, gives their fields. The key of the account is never written into the bot file or a file the project commits: it stays in the secrets file, under the `secret_name` the account section names.

   The sections are explained in Getting started, https://robottraders.io/lab/docs/getting-started.html#configure-the-bot. The next run executes an edit to a `.py` file as it is, and the next `uv run` installs the package again after an edit to its `pyproject.toml`.
3. **Ask the user whether to run a backtest** once the strategy can run, to check it works; they may want to go on coding first. On their yes, backtest `workspace/<name>` as the project instructions say, and tell the user whether its report shows the trades the strategy was meant to take.
4. **Ship the strategy when the user asks**, by following Ship a strategy, https://robottraders.io/lab/docs/ship-a-strategy.html, which holds every step: the private repository and the install on the VPS.

## The contract

These rules hold for every strategy. A strategy that breaks one still looks correct, and fails at start-up, on the first candle, or by trading on data it should not see.

1. **Imports come from the public gates only**: `robottraderslab` (`Symbol`, `TimeFrame`), `robottraderslab.strategies`, `robottraderslab.strategies.futures`, `robottraderslab.indicators` and `robottraderslab.exceptions`. `robottraderslab._internal` and every other subpackage are internal and change without notice.
2. **The shape is a profile class and a `ProfileStrategy` over it**: the profile is a frozen, keyword-only dataclass extending `Profile`, whose typed fields are built from each `[[strategy.profiles]]` section; a field `sizing: SizingRule` is built from the one key of the section naming a rule, such as `total_balance_ratio = 0.5`. The strategy class is `ProfileStrategy[MyProfile]` and declares `market_type: ClassVar[MarketType] = "futures"` and the annotation `account: FuturesAccount`. Every other `[strategy]` key sets the class attribute of the same name, so settings are typed class attributes with defaults and the strategy writes no `__init__`. A strategy whose logic does not split into profiles implements `StrategyProtocol` instead.
3. **`setup` declares everything read later**: one `requirements.ohlcv.add(symbol, timeframe, lookback=...)` per market, its `lookback` covering the longest indicator, and one `requirements.account.add(self.account, symbols=..., ...)` naming the state the snapshot serves (`positions`, `open_orders`, `triggers` for the resting trigger entries among the open orders, `balances`, the `sizing` rules). Reading state that was not declared raises `BotCriticalError` on the first candle, except the resting trigger entries: on a Bitget account `snapshot.open_orders(symbol)` omits them without `triggers`, and raises nothing; the other venues list them whatever it says.
4. **Signals are computed once over the whole series**: `ohlcvs.column(...)` returns the series as a numpy array and `ohlcvs.add_column(...)` stores a computed one, under a name carrying `profile.tag` when two profiles share a symbol and timeframe, so they never overwrite each other.
5. **Booking reads the current candle and nothing else**: `ohlcvs.current(...)` and `ohlcvs.signal(...)` read the candle the engine stands on and take no index, which is what keeps the future out of reach. A booking slot never indexes a column by position.
6. **Booking is synchronous and performs no I/O**: no `await`, no network, no exchange call, no file read. Account state comes from `account_snapshots.of(self.account)`, and every action goes through `bookkeeper.add(...)`; the engine executes the book after the slot returns. By default an action waits for every action booked before it, so the book runs in the order it was written. An action that depends on only some earlier actions names them, `bookkeeper.add(entry, after=cancel)`, and `after=()` waits for none: a live cycle then runs the actions that wait for nothing of each other at the same time, such as the orders of two symbols, while an order still waits for the cancel it names. A backtest always runs the book in the order it was written. For how to group and order actions so that the ones that depend on each other run in sequence: https://robottraders.io/lab/docs/implement-a-strategy.html#ordering-booked-actions
7. **An order is sized exactly once**: either `quantity=` on the entry or exit call, or the builder's `.size(rule, price, snapshot)` with the profile's `SizingRule`. `risk_ratio` sizes from the stop-loss, so its order carries `.stop_loss(price=...)`.
8. **Protections are restated on every candle**: a position the strategy protects gets `self.account.move_stop_loss(symbol, price)` booked whenever the snapshot reports it and the candle does not close it, and `self.account.move_take_profit(symbol, price)` too when it carries a take-profit, since the engine reads a protection back only in the cycle that booked it and a live run is one cycle, so a protection lost since an earlier cycle is restored only by the strategy booking it again; a candle whose level has no price (an indicator still in its warm-up, a NaN band) books no update and leaves the resting protection in place, since both calls raise `ValueError` on a NaN price.
9. **State a later live cycle needs is rebuilt from the venue**: instance attributes survive from candle to candle inside one run, and a live run ends with its cycle. One profile per symbol reads its position from the snapshot; several profiles on one symbol declare a position tracker in `setup` and tag their orders with `.tag(profile.order_tag)`, since the venue nets them into one position.
10. **A failure raises the class that says what it stops**, imported from `robottraderslab.exceptions`. A problem with one profile stops that profile alone and the other profiles keep trading: a check on one profile's own settings goes in the profile class's `__post_init__` and raises `ProfileConfigError`, which live takes that profile and every profile on its symbol out of the run, or, when the bot keeps a copy of its last working configuration file and the section came with an edit, runs that symbol from the copy in exit-only mode, and a profile slot that finds its profile cannot go on raises `ProfileError`, which live costs that profile the cycle; any other ordinary error (`ValueError`, `KeyError`) there stops the profile the same way, and an unknown key, a wrong type or a sizing error in a profile section refuses it too. `BotCriticalError` stops the whole bot wherever it is raised, a profile's `__post_init__` and its slots too, except in the check a live bot runs on an edited configuration file before trading it, where it counts as a failure of that file and the bot runs its copy of the last file that passed, and in `rtlab live --dry-run`, which prints it as a failure of the file: raise it only on purpose, for a problem that makes the whole bot unsafe to run, such as two profiles placing orders under the same tag on one symbol (a check across profiles, in `setup`), and tell the user that a live bot stopped this way leaves every open position with only the orders already resting on the venue until the configuration file is corrected and the bot runs again. In a backtest every one of these stops the run, `ProfileConfigError`, `ProfileError` and `BotCriticalError` with exit 78. The strategy never wraps a slot in `except Exception` and never catches an exchange error: the connector classifies it, and the engine retries what is worth retrying.
11. **A profile `tag` is at most 8 bytes** and carries none of `@`, `-`, `/`, `:` or a space.
12. **An order setting goes where the engine names it**: a concept the engine knows is a builder call or its keyword, such as `.limit(price, time_in_force=...)` or `trigger_type=` on `.trigger`, `.stop_loss` and `.take_profit`, whose `DEFAULT` watches the mark price, and the last trade for a take-profit; only a field one venue alone has goes in `.params("bitget", ...)`, addressed to that venue's connector, which refuses a field it sets itself. A setting a run may change is a typed class attribute passed to its call, and a run's `[orders]` section wins over the code.
13. **Nothing in the strategy is specific to a backtest or to live trading**: the engine runs the same class through the same calls in both, which is what lets a backtest stand for live trading. The strategy never checks which of the two it runs in and never branches on it; when the user asks for such a branch, warn them that the backtest would then no longer test the code that trades.
14. **An exit signal is a state, never an event**: the column an exit reads is raised on every candle the position's side is closed (`fast < slow` for a long), not on the candle of the crossing alone, and the booking slot books the exit for any held position, tracked or read from the snapshot, whose side the signals have closed. An exit the venue refused is then booked again on the next candle of the profile's timeframe with nothing remembered between cycles (rule 9); an exit raised on the crossing candle alone is booked once and a refusal leaves the position standing until the next crossing.
